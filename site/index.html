STAGE 02

Not every failure is recoverable, and some are harmful to touch

Retrying a payment that cannot succeed burns gateway fees, annoys customers, and trips issuer velocity limits that damage approval rates on good traffic. So every failure is sorted before anything is planned.

The Unclassified bucket is the one that matters. A real feed always contains reasons your taxonomy has not seen, and guessing at them is how a recovery system starts charging cards for reasons it does not understand. Two independent conditions must both hold before any silent retry: the class must permit one, and we must actually hold a reusable mandate. A payment can be retryable in principle and not retryable by us. recouper/detect/classify.py

STAGE 05

The number almost every recovery demo gets wrong

Most systems report gross recovery: “we chased 200 failed payments and ₹4 lakh came in.” But a large share of those customers would have paid anyway — the system emailed them first and took credit. So 20% of every batch is held out as an untouched control arm: no contact, no retry, not even a plan.

ADVERSARIAL

What happens when the model is on the attacker’s side

A customer types their own name at checkout. A gateway writes its own error description. Both are rendered into the planner’s prompt, so both are attacker-controlled. We assume the model is fully compromised — it reads the injected text and returns exactly the plan the attacker wanted, every time.

Assuming total compromise is the only version of this test worth running. Measuring how often Claude resists these prompts would produce a number about one model on one day — it would look good, and it would change with a version bump. What the architecture is responsible for is what an attacker gets when the model gives them everything. It also means containment is verified offline, with no API key, on every commit. python -m recouper.cli redteam · SECURITY.md

What the attacker still gets. Blocking the action is not the whole story — the text still flows. Attacker text reaches the audit rationale in 18 of 26 cases. That is not a leak: a ledger that discarded hostile input would be a worse ledger. It is stated because it has a consequence — anything rendering that log must treat it as untrusted. The customer-facing message body is template-derived from the debt amount alone and never carries it.

METHOD

Which conclusions survive being wrong about everything

Every outcome here is simulated — a test-mode API cannot make a synthetic customer decide to pay. So each conclusion is re-tested across a parameter space where every assumption may be wrong by up to a factor of two, with the agent’s behaviour held fixed.

ConclusionHolds inVerdict
Gross reporting overstates impact by ≥2×86%Robust — independent of the parameters
The intervention helps at all78%Likely, not established
One batch shows a >5pp lift39%Fails — included because it should

Costs moving the lift by exactly zero is the analysis’s own control: costs never enter the recovery probability, so any other value would mean the harness was wired wrong. A test asserts it stays zero.

The sweep corrected the project’s own documentation. An earlier draft named BASE_SELF_RECOVERY as the most consequential parameter; it is fourth. ACTION_ODDS_RATIO dominates by roughly 4× — so that is the number to attack if you want to argue with the result. Finding that out is what a sensitivity analysis is for. EVIDENCE

Every decision, including the refusals, is on the chain

An append-only JSONL ledger, each record hash-chained to its predecessor. Editing, deleting, reordering or forging a record breaks the chain and verify() reports the exact sequence number.

// one denial, exactly as written to runs/audit_seed42.jsonl { "seq": 53, "actor": "policy", "event": "action_denied", "case_id": "inv_yhTGHfODmiVBO0", "action": "send_reminder", "reason": "last contact was 0h ago; cooldown is 72h across all debts", "policy_checks": [ 9 rules, each with its own verdict and reason ], "detail": { "retryable_later": true }, "hash": "a3f1…", "prev": "9c04…" }
chain intact across 576 records

576 records for 340 cases, because denials, escalations and plans are logged alongside executed actions — roughly half the ledger is things the system decided not to do. This is not tamper-proof: anyone who can rewrite the file can recompute the chain. It makes casual tampering and accidental corruption detectable, which is the realistic threat for an operational log. python -m recouper.cli verify runs/audit_seed42.jsonl

Scope. All recovery outcomes are simulated under the documented model in recouper/outcomes/simulate.py; the contribution is the measurement framework and the bounded execution, not the rupee figure. No real customer data is used, no message is ever sent — the notification adapter is a logged no-op, and synthetic addresses use @example.invalid, reserved by RFC 2606. Simulation parameters were fixed before any recovery number was computed and have not been adjusted since.
